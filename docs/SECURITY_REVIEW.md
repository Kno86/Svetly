## Проверено без изменений

- Права проверяются на сервере (`@RequirePermission`, `@Authenticated`). Интеграционные тесты на PostgreSQL проверяют роль × endpoint, IDOR и admin API от обычного пользователя.
- Cookie `httpOnly` и `SameSite=Lax`, `Secure` в production. Проверяются CSRF и origin. Пароли хэшируются Argon2id.
- Журнал аудита только дополняется: триггер в БД. В логах вырезаются `authorization`, `cookie` и `set-cookie`.
- Контейнеры работают от пользователя `node`, есть healthchecks. Миграции выполняются отдельным сервисом. Наружу открыт только `web:3000`, Mailpit доступен только на `127.0.0.1`.
- Service worker кеширует только статику, после выхода из аккаунта кеш очищается (PHASE 9).
- axe (WCAG 2.2 A/AA, только автоматические правила): 0 нарушений на 10 страницах, desktop и mobile 360 px.

## Производительность (измерено)

- Публичные API на пустой БД через `:3000`: p50 2–5 мс, p95 ≤ 8 мс (20 запросов на endpoint).
- 50 000 новостей в отдельной БД:
  - список (`status`, `published_at DESC`, 20 записей) — Index Scan, 0,09 мс;
  - `count(*)` — Seq Scan, 27 мс;
  - поиск по частому слову — 73 мс, по запросу из двух слов — 270 мс (Parallel Seq Scan, потому что подходят почти все строки).
- Для масштаба посёлка этого достаточно. При росте контента до десятков тысяч записей стоит ограничить `ILIKE` по телу и считать `total` приблизительно.
- JS-бандл: самый крупный chunk — 72 КБ gzip.

## Остаточные риски

- Локальный запуск без Caddy (`:3000`): лимиты попыток общие для всех, а `X-Forwarded-For` можно подделать. Публиковать `web:3000` в интернет напрямую нельзя, только через Caddy (`compose.prod.yaml`).
- CSP разрешает `'unsafe-inline'` для скриптов: этого требует гидратация Next.js без nonce. Переход на nonce-CSP — отдельная задача.
- Нет внешнего мониторинга доступности и оповещений: провайдер не выбран. Есть `/api/health/live`, `/api/health/ready` и JSON-логи.
- Ручного аудита доступности (скринридер, клавиатура) и нагрузочного теста не было. Базовый нагрузочный тест — в PHASE 13.
