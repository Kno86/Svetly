# Готовность к запуску (PHASE 13)

Публичного запуска не было: домен не куплен, сервер не арендован, деньги не тратились. Всё ниже — подготовка и чек-листы. Каждый пункт, где нужны решение или деньги, отмечен **[владелец]**.

## 1. Production-конфигурация

- Запуск: `docker compose -f compose.yaml -f compose.prod.yaml --env-file .env.production up -d --build` (подробно в `docs/RUNBOOK.md`).
- `SVETLY_ENV=production` включает проверки при старте API:
  - API не стартует с dev-паролем базы (`*local_dev_only*`);
  - API не стартует без `https://` в `SVETLY_PUBLIC_URL`;
  - секрет авторизации (`BETTER_AUTH_SECRET`) обязателен.
- Наружу открыт только Caddy (80/443). Порт web `:3000` наружу не публикуется: без Caddy лимиты попыток входа работают по общему счётчику (`docs/SECURITY_REVIEW.md`).
- Секреты задаются только в `.env.production` на сервере. Файл не коммитится.
- Индексация поисковиками выключена, пока не задан `SVETLY_INDEXING=enabled`. Включать её только после проверки контента.

## 2. Домен и HTTPS — [владелец]

1. Купить домен и выбрать хостинг. Ориентир — VPS с 2 vCPU / 4 ГБ RAM / 40 ГБ SSD, Docker 27+.
2. DNS: записи `A`/`AAAA` домена указывают на сервер. Открыты порты 80 и 443.
3. Задать `SVETLY_DOMAIN` и `ACME_EMAIL`. Caddy сам получит и продлит сертификат Let's Encrypt.
4. Проверить: `curl -I https://<домен>`. В ответе должны быть HSTS, CSP и `X-Frame-Options: DENY`, а `/api/health/ready` должен отвечать `200`.
5. Настроить SMTP-провайдера (`SMTP_URL`, `MAIL_FROM`), SPF/DKIM/DMARC для домена отправителя. `compose.prod.yaml` не запустится без `SMTP_URL` и `MAIL_FROM`.

## 3. Мониторинг — [владелец]

Есть:

- `/api/health/live` — процесс жив;
- `/api/health/ready` — база и миграции;
- healthcheck в Docker;
- структурированные JSON-логи с `x-request-id`;
- журнал аудита.

Нужно выбрать внешний сервис:

- проверка `https://<домен>/api/health/ready` раз в 1–5 минут с оповещением в Telegram или на почту (например, UptimeRobot или Healthchecks.io, у многих есть бесплатный тариф);
- оповещение, если ночной backup не выполнился (heartbeat после `backup.sh`);
- ротация логов Docker (`max-size`, `max-file`) на сервере;
- контроль свободного места на диске.

## 4. Backup и учебное восстановление

- Ежедневно по cron: `infra/scripts/backup.sh` (база + фото, контрольная сумма). Копию хранить вне сервера **[владелец: где хранить]**.
- Раз в месяц и перед каждым обновлением: `infra/scripts/restore-test.sh <dump> <media.tar.gz>`. Восстановление идёт в изолированный проект, живая база не затрагивается.
- Учебное восстановление проводилось в PHASE 10: база и фото восстановлены, проверка `PASSED`.
- Цели: потеря данных не больше 24 ч (RPO), восстановление не дольше 2 ч (RTO). Это ориентиры, на production-сервере не проверены.

## 6. Готовность контента

Ориентир из ТЗ — 20–30 полезных материалов и 10–15 бизнесов или специалистов **с их согласия**. Имитировать активность нельзя.

- [ ] Создан первый Super Admin (`node dist/cli.js admin:create`), назначены редактор и модератор.
- [ ] Новости и справочник: только проверенные сведения с источником.
- [ ] Организации: карточка с согласия владельца, отметку «проверено» ставит администратор с указанием способа проверки.
- [ ] События: реальные, с датой и организатором.
- [ ] Пустые разделы показывают честные пустые состояния (так и реализовано).

## 7. Аналитика

Аналитика уже встроена (`docs/ANALYTICS.md`): DAU/WAU/MAU, источники и UTM, поиск без результатов, ключевые действия. IP, данные браузера и id пользователя не хранятся. Метрики первого месяца:

- реальные регистрации;
- публикации;
- заявки бизнесу;
- обращения;
- повторные визиты.

Посещения сами по себе метрикой успеха не считаются.
